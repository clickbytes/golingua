# Typed question execution

`internal/reason.Plan` accepts a typed `MeaningGraph`, request context and an explicit `RelationMapping` supplied by a trusted caller. The graph must have one question discourse act and one question scope over an event/state predicate. The caller maps two declared CORE semantic roles to the argument positions of one binary CORE relation. The catalog compiles these relations only from event concepts with exactly two declared roles, preserving event identity, role order and endpoint kinds. Text labels and lexical similarity never choose the relation.

Every grounded participant must resolve through a request `Mention` to one `ReferentID`. A WH question leaves exactly one mapped role absent; its answer candidates are request referents whose CORE kinds fit the missing relation argument. Yes/no questions have two grounded arguments. Unsupported operator scopes, unresolved identity, missing role mappings or unsupported shapes produce typed outcomes instead of a guess.

`Execute` delegates yes/no truth to the bounded reasoner. `true` and `false` require positive proof or direct negative evidence. Opposing evidence is `conflict`; no evidence is `unknown`. WH execution evaluates each bounded, type-compatible referent and returns all positive or conflicting candidates with proof evidence. Multiple candidates are `ambiguous`; it never selects the first. Answers contain stable referent IDs, not surface words.

The `question` CLI accepts this typed request and can optionally realize a response with `--language pl|en`. It does not parse natural-language questions. Positive yes/no answers can use the existing approved statement routes; generated tense, person/number and English definiteness are explicit assumptions, so the current surfaces report `incomplete`. False answers require negation, and WH answers require a standalone NP construction; until those target routes are registered, the CLI returns `unsupported` for the surface while preserving the structured answer and its evidence.

The bounded agent evaluation uses one request-scoped demonstration fact, which is not persisted and is not owner-authored. Owner acceptance of the reasoning or language output remains a separate status.
